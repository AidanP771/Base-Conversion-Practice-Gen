1. How number bases work

A number base (or radix) is just how many symbols you count with before you roll over into another digit. Decimal uses 10 symbols, 0 through 9, because most humans have 10 fingers. There is nothing mathematically special about 10.

Every digit in a number has a place value: a power of the base, based on its position counting from the right, starting at position 0. In decimal, the digits of 202 are worth 2×102, 0×101, and 2×100. Add those up and you get 202 back, which sounds circular, but it is exactly the same process any base uses.

Computers use binary (base 2) because a transistor or a wire is most reliably read as one of two states: on or off, high voltage or low voltage. Trying to reliably distinguish 10 different voltage levels in hardware is far harder and far more error-prone than distinguishing 2.

The trouble with binary is that it is long. A byte like 11001010 is hard to read and easy to mistype. Hex (base 16) and octal (base 8) exist purely as compact stand-ins for binary: because 16 and 8 are powers of 2, each hex or octal digit lines up exactly with a fixed group of bits (4 bits for hex, 3 for octal), so you can convert between them by grouping instead of doing any arithmetic. That grouping trick is lessons 4 and 5.

2. Any base to decimal

To read a number in any base as decimal, multiply each digit by its place value (the base raised to the digit's position, counting from 0 on the right) and add up the results. Digits that are 0 contribute nothing, so you can skip them.

This works identically for binary, octal, and hex. The only difference is the base you raise to a power, and, for hex, remembering that A through F stand for 10 through 15.

3. Decimal to any base

Going the other way, from decimal into another base, uses repeated division instead of multiplication. Divide the decimal number by the target base, write down the remainder, then divide the quotient again, and keep going until the quotient is 0. The remainders, read from the last one back to the first (bottom to top, if you wrote them in a column), are the digits of the answer.

Why does this work? Each division peels off one digit's worth of place value, starting from the smallest place (position 0) and working up. Reading the remainders bottom to top puts them back in the normal order, most significant digit first.

4. Binary to hex and octal by grouping, and back

Because 16 is 24, every hex digit corresponds to exactly 4 bits. So to convert binary to hex, pad the binary number on the left with zeros until its length is a multiple of 4, split it into groups of 4 from the right, and convert each group to a single hex digit. No arithmetic on the whole number is needed, only on 4 bits at a time.

Octal works the same way with groups of 3 bits, since 8 is 23.

Going back from hex or octal to binary is the same idea in reverse: write each digit as its fixed-width group of bits (4 bits per hex digit, 3 per octal digit) and join the groups together, dropping only the extra leading zeros on the very first group.

5. Hex to octal through binary

There is no direct grouping trick between hex and octal, because their group sizes (4 bits and 3 bits) do not line up with each other. The practical route is to treat binary as a common middle step: expand the hex digits into bits, then regroup those same bits into octal digits.

This is exactly the grouping method from lesson 4, applied twice, once in each direction, with the full binary string as the thing that gets passed between them.

6. Signed numbers and why they are tricky

Everything so far has been unsigned: a bit pattern that only ever means a positive number (or zero). Real programs need negative numbers too, and a fixed-width bit pattern has to encode the sign somehow, using the same bits it would otherwise use for magnitude.

The most obvious idea is sign-magnitude: reserve the leftmost bit purely as a sign flag (0 for positive, 1 for negative) and let the remaining bits hold the ordinary binary magnitude. An 8-bit sign-magnitude 5 is 00000101, and -5 is 10000101, just that same pattern with the top bit flipped.

Sign-magnitude is easy to understand, but it is awkward for hardware: it produces two different bit patterns for zero (00000000 and 10000000), and ordinary binary addition does not just work on sign-magnitude numbers, addition hardware would need special-case logic for negatives. That is the problem that one's complement and two's complement were each invented to solve, in different ways. Sign-magnitude itself is not used in this app's practice modes; it is here only so the next two lessons have something to compare against.

7. One's complement

One's complement represents a negative number by writing its magnitude in binary and then flipping every bit (a bitwise NOT). To decode a one's complement pattern, look at the leftmost bit: if it is 0, read the rest as an ordinary positive binary number; if it is 1, flip every bit back and read the result as the magnitude, then apply a minus sign.

One's complement still has the two-zeros problem: all zeros is positive zero, and all ones is negative zero, and both mean the value 0. It also has a slightly awkward range, from -(2n-1 - 1) to 2n-1 - 1 for an n-bit pattern, one less negative value than you might expect, because that extra slot is spent on negative zero.

8. Two's complement

Two's complement fixes one's complement's remaining flaw. To encode a negative number, write its magnitude in binary, flip every bit, and then add 1. That last step is the whole difference from one's complement, and it is what removes the extra negative zero: the all-ones pattern that used to mean -0 now, with 1 added, wraps around and decodes as -1 instead.

To decode, the same idea in reverse works: if the leftmost bit is 0, read the rest as plain binary. If it is 1, flip every bit, add 1, and that is the magnitude of a negative number.

There is a useful shortcut for decoding two's complement without flip-and-add-1: treat the leftmost bit as having a place value of -2n-1 instead of the usual positive one, and add up all the place values normally, letting that one bit be negative. It gives the same answer directly.

Because there is exactly one bit pattern for zero, two's complement gets one extra negative value that one's complement cannot represent: its range is -2n-1 to 2n-1 - 1, not symmetric. That asymmetry is also why two's complement can overflow silently in the negative direction: negating the most negative value (for example, -128 in 8 bits) has no representable positive result, since +128 does not fit, and the hardware just wraps back around to -128. Two's complement won out over one's complement and sign-magnitude and is what essentially every modern computer uses, because ordinary binary addition and subtraction hardware works on it unmodified, with no extra sign-handling logic needed.

9. How floating point is laid out

Integers, signed or not, cannot represent fractions. IEEE 754 floating point solves that by storing a number in a form similar to scientific notation: a sign, a significand (also called a mantissa or fraction) that holds the significant digits, and an exponent that says how far to shift the point.

A single-precision (32-bit) float splits those into 1 sign bit, 8 exponent bits, and 23 fraction bits. Values are normalized so the significand always starts with an implicit 1 before the point, written 1.fraction, and that leading 1 is never actually stored since it is always there for any nonzero normal number. The exponent is stored biased, meaning a fixed offset (127 for single precision) is added to the true exponent before storing it, so the stored field is always non-negative and can be compared as a plain unsigned integer.

Put together, a single-precision value's true meaning is (-1)sign × 1.fraction × 2exponent - 127.

10. Converting a decimal to IEEE 754 single precision

  1. Work out the sign bit from whether the value is negative.
  2. Convert the integer part of the magnitude to binary.
  3. Convert the fractional part by doubling it repeatedly: each time the result reaches 1 or more, that step's bit is 1 and you drop the 1; otherwise the bit is 0. Keep going until the fraction is exactly 0 or you have enough bits.
  4. Slide the point so the number reads 1.xxxx × 2e, and note e.
  5. Add the bias (127) to e and write that as an 8-bit binary number: the exponent field.
  6. Drop the leading 1 from the normalized form and pad the rest on the right with zeros out to 23 bits: the fraction field.
  7. Lay the three fields side by side, sign then exponent then fraction, and read the result in hex, 4 bits at a time.

11. IEEE 754 single precision back to decimal

  1. Split the 32 bits into sign (1 bit), exponent (8 bits), and fraction (23 bits).
  2. Read the sign bit directly.
  3. Subtract the bias (127) from the exponent field to get the true exponent.
  4. Put the implicit leading 1 back in front of the fraction bits: 1.fraction.
  5. Shift that binary point by the true exponent (multiply by 2 raised to that power).
  6. Convert the resulting binary value to decimal.

12. Double precision: what changes

Double precision (64-bit) uses the exact same layout idea as single precision, just with wider fields: 1 sign bit, 11 exponent bits, and 52 fraction bits, with a bias of 1023 instead of 127. Every step from lessons 10 and 11 is identical; only the field widths and the bias number change.

The extra exponent bits give double precision a far larger representable range, and the extra fraction bits give it much finer precision, which is why it is the default choice in most programming languages when precision matters more than memory. Because 64 bits of binary is unwieldy to read at a glance, this app always shows double-precision bit patterns as 16 hex digits rather than spelling out all 64 bits, except inside a worked solution, where the bits are shown grouped by field.

13. Special values: zero, infinity, NaN, and subnormals

A few bit patterns in IEEE 754 are reserved for values that do not fit the normal 1.fraction × 2exponent - bias scheme.

Zero is exponent all 0s and fraction all 0s. The sign bit still applies, so there are two zero bit patterns, +0 and -0, which compare as equal but are not bit-identical.

Infinity is exponent all 1s and fraction all 0s. The sign bit gives +Infinity or -Infinity, produced by things like dividing a nonzero number by zero, or a value too large to represent.

NaN (Not a Number) is exponent all 1s with a nonzero fraction. Any nonzero fraction counts as some NaN, which is why invalid operations like 0/0 or the square root of a negative number produce it. This app always shows the canonical quiet NaN, with only the top fraction bit set, as its answer, but accepts any valid NaN pattern you type.

Subnormals (sometimes called denormals) fill the gap between zero and the smallest normal value. They use an exponent field of all 0s, like zero, but a nonzero fraction, and unlike every other case, they have no implicit leading 1: the value is just 0.fraction × 21 - bias. This lets floating point underflow gradually toward zero instead of jumping straight from the smallest normal value to nothing.
